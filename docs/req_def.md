# CVAT向け骨格推定モデル自動デプロイファイル生成Webアプリ 要件定義書

## 1. 概要

本アプリケーションは、CVATで自作YOLO系の骨格推定モデルを自動アノテーション機能として利用するために必要なNuclio関数ファイル一式を自動生成するローカルWebアプリケーションである。

ユーザーはWebブラウザから、作成者名、モデル表示名、SVGファイル、YOLOの`.pt`重みファイルをアップロードする。

アプリケーションは、入力内容とSVGから取得した情報をもとに、CVATのデプロイexampleをベースとした以下の4ファイルを生成し、1つのフォルダにまとめてzip形式でダウンロードできるようにする。

- `function.yaml`
- `main.py`
- `model.onnx`
- `model_handler.py`

本アプリケーションは、生成したファイルをCVAT/Nuclio環境に配置してデプロイできる状態にすることを目的とする。

CVATへの自動デプロイそのものはMVPでは行わない。

## 2. 開発目的

CVATで自作YOLO系骨格推定モデルを自動アノテーションとして利用するには、モデルファイルだけでなく、CVAT/Nuclio用の設定ファイルや推論処理コードを用意する必要がある。

手作業では以下のような作業が必要になり、煩雑である。

- CVAT/Nuclio用のディレクトリ構成を作成する
- `function.yaml`をモデルに合わせて書き換える
- `main.py`をCVATの入出力形式に合わせて用意する
- `model_handler.py`をモデルの推論処理に合わせて用意する
- YOLOの`.pt`ファイルをONNX形式に変換する
- SVGから必要なモデル情報やラベル情報を反映する
- 作成したファイルをデプロイ可能な形にまとめる

本アプリケーションは、これらの作業をWeb画面上の簡単な入力とファイルアップロードだけで自動化することを目的とする。

## 3. 想定利用環境

本アプリケーションは、外部公開用のWebサービスではなく、研究室や社内LANなどのローカルネットワーク内で利用することを想定する。

### 3.1 アクセス方法

アプリケーションはローカルサーバ上で起動し、同一LAN内のPCからIPアドレスでアクセスできるようにする。

例:

```text
http://192.168.1.100:8000
```

### 3.2 サーバ起動条件

Webサーバは`0.0.0.0`で待ち受ける。

例:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 4. 想定ユーザー

本アプリケーションの主な利用者は、CVATで自作YOLO系骨格推定モデルを自動アノテーションに利用したい研究者、学生、開発者である。

利用者は以下のような状態を想定する。

- YOLO系骨格推定モデルの学習済み`.pt`ファイルを持っている
- CVATでアノテーション作業を行っている
- CVATの自動アノテーション機能を使いたい
- Nuclio用ファイルを毎回手作業で作成するのが面倒である
- 技術的にコマンドプロンプトをうまく扱えない

## 5. 基本方針

### 5.1 CVAT exampleをベースにする

`function.yaml`、`main.py`、`model_handler.py`はゼロから生成するのではなく、CVATのデプロイexampleをベーステンプレートとして利用する。

対象モデルは骨格推定モデルであるため、基本的にはCVATの骨格推定モデル用exampleをベースにする。

ただし、骨格推定モデル用exampleに不足しているデプロイ設定がある場合は、物体検出モデル用exampleの記述を参考にして、骨格推定モデル向けに適切に調整する。

### 5.2 生成対象は4ファイルのみ

本アプリケーションが生成する成果物は以下の4ファイルのみとする。

- `function.yaml`
- `main.py`
- `model.onnx`
- `model_handler.py`

以下のファイルは生成しない。

- `icon.svg`
- `deploy_cpu.sh`
- `deploy_gpu.sh`
- `README.md`

### 5.3 SVGは設定情報の入力元として使う

SVGファイルはアイコンとして出力するためのものではなく、モデル内部名やラベル情報を自動取得するための入力ファイルとして扱う。

SVGファイルは解析後、生成されるzipには含めない。

### 5.4 `.pt`はONNXに変換する

ユーザーはYOLO系骨格推定モデルの`.pt`ファイルをアップロードする。

アプリケーションはサーバ側で`.pt`をONNX形式に変換し、`model.onnx`として生成フォルダに配置する。

### 5.5 複数人同時利用に対応する

複数人が同時にアクセスしても、アップロードファイルや生成ファイルが混ざらないようにする。

そのためにRedisを使用し、ジョブキュー、進捗状態、一時ファイル情報を管理する。

### 5.6 Docker Composeで起動できる構成にする

開発環境と実行環境の差異を小さくするため、本アプリケーションはDocker Composeで起動できる構成にする。

## 6. 入力項目

Webフォームでユーザーが入力する項目は以下の4つとする。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 作成者名 | 必須 | 生成ファイル内のメタ情報やコメントに使用する |
| モデル表示名 | 必須 | CVAT上に表示されるモデル名として使用する |
| SVGファイル | 必須 | モデル内部名およびラベル情報を自動取得するために使用する |
| `.pt`ファイル | 必須 | YOLO系骨格推定モデルの学習済み重みファイル。ONNXへ変換して`model.onnx`として出力する |

以下の項目は、ユーザー入力欄としては用意しない。

- モデル内部名
- ラベル一覧
- confidence threshold
- NMS threshold
- image size
- ONNX opset

必要な固定値や既定値は、アプリケーション設定またはテンプレート側で管理する。

## 7. SVGから自動取得する情報

アップロードされたSVGファイルから、以下の情報を自動的に読み取る。

- モデル内部名
- ラベル情報

骨格推定モデルを対象とするため、ラベル情報には通常のクラス名だけでなく、keypointやskeleton構造に関する情報が含まれる可能性がある。

SVGからどのように情報を抽出するかの詳細は、別途提示されるSVG解析仕様に従う。

### 7.1 モデル内部名

モデル内部名は以下に使用する。

- 出力フォルダ名
- zipファイル名
- Nuclio関数名
- `function.yaml`内の関数識別名

モデル内部名は、ファイル名や関数名として安全に使える形式に変換する。

使用可能文字は以下とする。

- 英小文字
- 数字
- ハイフン
- アンダースコア

変換例:

```text
SVGから取得した名前: My Pose Model
内部名: my-pose-model
```

### 7.2 ラベル情報

SVGから取得したラベル情報は、以下に反映する。

- `function.yaml`
- `model_handler.py`

取得後、以下のチェックを行う。

- 1つ以上のラベル情報が存在すること
- 空文字のラベル名が存在しないこと
- 重複ラベルが存在しないこと
- 前後の空白を除去すること
- 骨格推定用の定義として破綻していないこと

### 7.3 SVG解析エラー

SVGから必要な情報を取得できない場合は、ジョブを開始せず、画面にエラーを表示する。

エラー例:

- SVGファイルからモデル内部名を取得できませんでした
- SVGファイルからラベル情報を取得できませんでした
- SVGファイル内のラベルが重複しています
- SVGファイルの形式が不正です
- 骨格推定用のラベル定義として不正です

## 8. 出力ファイル構成

生成されるzipファイルを展開すると、以下の構成になる。

```text
<model_internal_name>/
├── function.yaml
├── main.py
├── model.onnx
└── model_handler.py
```

zipファイル名は以下とする。

```text
cvat-yolo-<model_internal_name>.zip
```

例:

```text
cvat-yolo-human-pose.zip
```

SVGファイル、`.pt`ファイル、README、デプロイスクリプトはzipに含めない。

## 9. CVAT exampleテンプレートの調整方針

本アプリケーションで生成する`function.yaml`、`main.py`、`model_handler.py`は、CVATのデプロイexampleをベーステンプレートとして使用する。

対象モデルはYOLO系の骨格推定モデルである。

そのため、基本的にはCVATの骨格推定モデル用exampleをベースにする。

ただし、CVATの骨格推定モデル用exampleには、実行環境やデプロイ設定に関して不足している項目がある可能性がある。

物体検出モデル用exampleには含まれているが、骨格推定モデル用exampleには含まれていない設定がある場合は、物体検出モデル用exampleの記述を参考にして、骨格推定モデル向けに適切に調整する。

### 9.1 調整対象

主に以下を確認し、必要に応じて骨格推定モデル用テンプレートへ反映する。

- `function.yaml`
- `main.py`
- `model_handler.py`

特に`function.yaml`については、Nuclio/CVATでのデプロイ時に必要な設定が不足しないようにする。

### 9.2 調整方針

以下の優先順位でテンプレートを作成する。

1. 骨格推定モデル用exampleの構造を優先する
2. 不足しているデプロイ設定のみ物体検出モデル用exampleを参考に補う
3. モデル種別に依存する処理は骨格推定向けに維持する

物体検出モデル用exampleの設定をそのままコピーするのではなく、骨格推定モデルの入出力形式、ラベル定義、skeleton定義、`model_handler.py`の後処理に合わせて調整する。

### 9.3 変更箇所

`function.yaml`、`main.py`、`model_handler.py`の具体的な変更箇所は、別途ユーザーがClaude Codeに提示する仕様に従う。

本要件定義では、変更箇所の詳細までは固定しない。

## 10. 推奨技術構成

### 10.1 バックエンド

FastAPI。

FastAPIを推奨する理由:

- ファイルアップロードAPIを作りやすい
- 進捗確認APIを作りやすい
- ダウンロードAPIを作りやすい
- OpenAPIドキュメントが自動生成される
- 非同期処理と相性がよい

### 10.2 ジョブ管理

- Redis
- RQ

MVPでは実装が比較的簡単なRQを優先する。

構成:

```text
FastAPI + Redis + RQ + Worker
```

### 10.3 フロントエンド

MVPではシンプルなHTMLフォームでよい。

候補:

- Jinja2 templates
- HTML
- CSS
- JavaScript

ReactなどのSPAはMVPでは不要とする。

### 10.4 モデル変換

`.pt`から`.onnx`への変換には、Ultralytics YOLOのexport機能を利用する。

## 11. Docker構成

本アプリケーションはDocker Composeで起動できる構成とする。

構成するサービスは以下の3つとする。

- web
- worker
- redis

### 11.1 web

FastAPIによるWebアプリケーションを担当する。

主な役割:

- Web画面表示
- フォーム入力受付
- ファイルアップロード
- ジョブ作成
- 進捗確認API
- zipダウンロードAPI

### 11.2 worker

Redisキューからジョブを取得し、重い処理を実行する。

主な役割:

- SVG解析
- `.pt`から`model.onnx`への変換
- テンプレートファイル生成
- 出力フォルダ作成
- zip作成
- ジョブ状態更新

### 11.3 redis

ジョブキュー、進捗状態、一時ファイル情報を管理する。

### 11.4 共有ストレージ

webサービスとworkerサービスは、アップロードファイルと生成ファイルを共有するため、同一のstorage volumeをマウントする。

例:

```text
/storage
```

### 11.5 起動イメージ

```bash
docker compose up --build
```

LAN内の別PCからは以下のようにアクセスする。

```text
http://<server-ip>:8000
```

## 12. 全体処理フロー

1. ユーザーがWebアプリにアクセス
2. 作成者名、モデル表示名、SVGファイル、`.pt`ファイルを入力
3. フォーム送信
4. 入力値を検証
5. SVGを解析し、モデル内部名とラベル情報を取得
6. ジョブIDを発行
7. アップロードファイルをジョブごとの一時ディレクトリに保存
8. Redisにジョブを登録
9. Workerがジョブを取得
10. `.pt`を`model.onnx`へ変換
11. CVAT exampleテンプレートから`function.yaml`を生成
12. CVAT exampleテンプレートから`main.py`を生成
13. CVAT exampleテンプレートから`model_handler.py`を生成
14. 4ファイルを1つのフォルダにまとめる
15. zip化
16. ジョブ状態を`success`に更新
17. ユーザーがzipをダウンロード

## 13. 一時ディレクトリ構成

一時ディレクトリは以下のようにする。

```text
/storage/jobs/
├── <job_id>/
│   ├── input/
│   │   ├── model.pt
│   │   └── model.svg
│   ├── output/
│   │   └── <model_internal_name>/
│   │       ├── function.yaml
│   │       ├── main.py
│   │       ├── model.onnx
│   │       └── model_handler.py
│   └── cvat-yolo-<model_internal_name>.zip
```

アップロードされたSVGと`.pt`は入力用として保存するが、最終zipには含めない。

## 14. 入力チェック要件

### 14.1 作成者名

- 必須
- 空文字を許可しない
- 前後の空白は除去する

### 14.2 モデル表示名

- 必須
- 空文字を許可しない
- 前後の空白は除去する
- CVAT上に表示される名称として利用する

### 14.3 SVGファイル

- 必須
- 拡張子`.svg`のみ許可
- SVGとして解析できること
- モデル内部名を取得できること
- ラベル情報を取得できること
- ファイルサイズ上限を設ける

### 14.4 `.pt`ファイル

- 必須
- 拡張子`.pt`のみ許可
- ファイルサイズ上限を設ける
- アップロードされたファイルはジョブごとの一時ディレクトリに保存する
- 処理完了後、一定時間で削除する

### 14.5 モデル内部名

モデル内部名はSVGから取得する。

ユーザー入力欄としては用意しない。

取得したモデル内部名は、ファイル名や関数名として安全な形式に正規化する。

許可文字:

- 英小文字
- 数字
- ハイフン
- アンダースコア

### 14.6 ラベル情報

ラベル情報はSVGから取得する。

ユーザー入力欄としては用意しない。

取得したラベル情報は、骨格推定モデル用の定義として不正がないか検証する。

## 15. 機能要件

### F-01 Webフォーム表示

ユーザーが以下を入力できるWebフォームを表示する。

- 作成者名
- モデル表示名
- SVGファイル
- `.pt`ファイル

### F-02 入力チェック

フォーム送信時に入力値を検証する。

不正な値がある場合は、ジョブを作成せず、画面にエラーメッセージを表示する。

### F-03 SVGアップロード

ユーザーがアップロードしたSVGファイルを、ジョブIDごとの一時ディレクトリに保存する。

保存先例:

```text
/storage/jobs/<job_id>/input/model.svg
```

### F-04 `.pt`アップロード

ユーザーがアップロードした`.pt`ファイルを、ジョブIDごとの一時ディレクトリに保存する。

保存先例:

```text
/storage/jobs/<job_id>/input/model.pt
```

### F-05 SVG解析

アップロードされたSVGファイルを解析し、以下を取得する。

- モデル内部名
- ラベル情報

SVG解析に失敗した場合は、ジョブを開始しない。

### F-06 ジョブ作成

入力チェックおよびSVG解析に成功したら、Redisに生成ジョブを登録する。

ジョブには以下の情報を含める。

```json
{
  "job_id": "uuid",
  "status": "queued",
  "author": "作成者名",
  "display_name": "モデル表示名",
  "function_name": "svgから取得したモデル内部名",
  "labels": ["svgから取得したラベル情報"],
  "pt_path": "/storage/jobs/<job_id>/input/model.pt",
  "svg_path": "/storage/jobs/<job_id>/input/model.svg"
}
```

### F-07 ジョブ進捗表示

ユーザーはブラウザ上でジョブの進捗状態を確認できる。

状態は以下を想定する。

- `queued`
- `running`
- `parsing_svg`
- `exporting_onnx`
- `generating_files`
- `creating_zip`
- `success`
- `failed`
- `expired`

画面表示例:

- 待機中
- SVG解析中
- ONNX変換中
- ファイル生成中
- zip作成中
- 完了
- 失敗

### F-08 ONNX変換

Workerはアップロードされた`.pt`ファイルを読み込み、ONNX形式へ変換する。

出力ファイル名は必ず以下とする。

```text
model.onnx
```

保存先例:

```text
/storage/jobs/<job_id>/output/<model_internal_name>/model.onnx
```

ONNX変換に失敗した場合は、ジョブ状態を`failed`に変更し、エラーメッセージを保存する。

### F-09 `function.yaml`生成

CVAT exampleの`function.yaml`をベーステンプレートとして利用し、ユーザー入力およびSVG解析結果に応じて必要箇所を差し替える。

主な反映項目:

- 作成者名
- モデル表示名
- モデル内部名
- ラベル情報
- 骨格推定用のメタ情報
- 必要なNuclio/CVATデプロイ設定

変更箇所の詳細は、別途ユーザーがClaude Codeに提示する仕様に従う。

### F-10 `main.py`生成

CVAT exampleの`main.py`をベーステンプレートとして利用し、必要箇所を差し替える。

主な反映項目:

- モデルファイル名
- `model_handler.py`との連携部分
- 骨格推定モデル用の入出力処理

変更箇所の詳細は、別途ユーザーがClaude Codeに提示する仕様に従う。

### F-11 `model_handler.py`生成

CVAT exampleの`model_handler.py`をベーステンプレートとして利用し、SVG解析結果およびモデル構成に応じて必要箇所を差し替える。

主な反映項目:

- ラベル情報
- keypoint情報
- skeleton情報
- `model.onnx`の読み込みパス
- 骨格推定モデルの後処理
- CVATへ返す結果形式

変更箇所の詳細は、別途ユーザーがClaude Codeに提示する仕様に従う。

### F-12 フォルダ生成

生成した以下の4ファイルを1つのフォルダにまとめる。

- `function.yaml`
- `main.py`
- `model.onnx`
- `model_handler.py`

フォルダ名には、SVGから取得して正規化したモデル内部名を使用する。

```text
<model_internal_name>/
```

### F-13 zip生成

出力フォルダをzip化する。

zipファイル名:

```text
cvat-yolo-<model_internal_name>.zip
```

### F-14 ダウンロード

生成完了後、ユーザーはzipファイルをダウンロードできる。

ダウンロードURLには、他ユーザーのファイルを不用意に取得できないよう、job IDまたはdownload tokenを含める。

例:

```text
/download/<job_id>?token=<download_token>
```

### F-15 エラー表示

処理中にエラーが発生した場合、ユーザーにエラー内容を表示する。

表示するエラー例:

- SVGファイルの解析に失敗しました
- SVGファイルからモデル内部名を取得できませんでした
- SVGファイルからラベル情報を取得できませんでした
- ONNX変換に失敗しました
- `function.yaml`の生成に失敗しました
- `main.py`の生成に失敗しました
- `model_handler.py`の生成に失敗しました
- zipファイルの作成に失敗しました
- アップロードされたファイルが不正です

## 16. Redis利用要件

Redisは以下の用途で利用する。

### 16.1 ジョブキュー

`.pt`から`model.onnx`への変換やファイル生成処理は、Webリクエスト内で直接実行しない。

Redisキューにジョブを登録し、Workerが順番に処理する。

### 16.2 ジョブ状態管理

ジョブごとに以下の情報をRedisへ保存する。

```json
{
  "job_id": "uuid",
  "status": "running",
  "progress": 60,
  "message": "Exporting model.onnx...",
  "created_at": "2026-07-02T10:00:00+09:00",
  "updated_at": "2026-07-02T10:01:30+09:00",
  "zip_path": "/storage/jobs/<job_id>/cvat-yolo-model.zip",
  "download_token": "random-token"
}
```

### 16.3 同時利用時の分離

各ジョブは必ず一意の`job_id`を持つ。

ジョブごとに以下を分離する。

- アップロードファイル
- 生成ファイル
- zipファイル
- 進捗状態
- エラー情報
- ダウンロードトークン

### 16.4 Worker数

MVPでは、変換および生成処理を行うWorkerは1つでよい。

理由:

- ONNX変換はCPU/RAM負荷が高い
- 複数同時に変換するとサーバが不安定になる可能性がある
- 複数人がアクセスしても、変換処理は順番待ちにすればよい

## 17. 一時ファイル管理要件

### 17.1 自動削除

生成済みファイルは一定時間後に削除する。

目安:

- 成功ジョブ: 1時間後に削除
- 失敗ジョブ: 30分後に削除
- アップロード途中の残骸: 定期削除

### 17.2 永続保存しない

アップロードされた`.pt`ファイル、SVGファイル、生成された`model.onnx`は、原則として永続保存しない。

### 17.3 ファイル名の安全性

ユーザー入力やSVGから取得した文字列を、ファイルパスとしてそのまま使用しない。

必ず正規化したモデル内部名やUUIDを使用する。

### 19.1 トップ画面


```http

```


## 20. 非機能要件

### 20.1 ローカルネットワーク対応

同一LAN内からIPアドレスでアクセスできること。

### 20.2 同時アクセス対応

複数ユーザーが同時にアクセスしても、処理内容が混ざらないこと。

### 20.3 安定性

重い処理であるONNX変換はWebプロセスではなくWorkerで実行すること。

### 20.4 セキュリティ

ローカルネットワーク内利用を前提とするが、最低限以下を満たす。

- 外部公開を前提にしない
- アップロードファイルの拡張子を検証する
- ファイルサイズ上限を設ける
- `job_id`をUUIDにする
- download tokenを発行する
- アップロードファイルを一定時間後に削除する
- ユーザー入力をファイルパスにそのまま使わない
- SVG解析時に外部参照や危険なXML処理を避ける

### 20.5 保守性

CVAT exampleをテンプレートとして管理し、ユーザー入力やSVG解析結果による差し替え箇所を明確にする。

テンプレートは以下のように管理する。

```text
templates/
└── cvat_pose_example/
    ├── function.yaml.j2
    ├── main.py.j2
    └── model_handler.py.j2
```

### 20.6 拡張性

将来的に以下を追加できる構成にする。

- ONNXファイル直接アップロード対応
- CVATへの自動デプロイ
- ユーザー管理
- 生成履歴管理
- 複数テンプレート切り替え
- 物体検出モデル対応
- segmentationモデル対応

## 22. 受け入れ条件

### AC-01 入力フォーム

Webフォームには以下の項目のみが表示されること。

- 作成者名
- モデル表示名
- SVGファイル
- `.pt`ファイル

### AC-02 SVG解析

ユーザーがSVGファイルをアップロードすると、アプリケーションがSVGからモデル内部名とラベル情報を取得できること。

### AC-03 SVG解析失敗時

SVGからモデル内部名またはラベル情報を取得できない場合、ジョブを開始せず、画面にエラーを表示すること。

### AC-04 ジョブ作成

ユーザーが作成者名、モデル表示名、SVGファイル、`.pt`ファイルを入力して送信すると、ジョブが作成されること。

### AC-05 ONNX変換

アップロードされた`.pt`ファイルから`model.onnx`が生成されること。

### AC-06 ファイル生成

以下の4ファイルが生成されること。

- `function.yaml`
- `main.py`
- `model.onnx`
- `model_handler.py`

### AC-07 zip構成

ダウンロードしたzipを展開すると、以下の構成になっていること。

```text
<model_internal_name>/
├── function.yaml
├── main.py
├── model.onnx
└── model_handler.py
```

### AC-08 余計なファイルを含めない

zip内に以下のファイルが含まれていないこと。

- SVGファイル
- `.pt`ファイル
- `README.md`
- `icon.svg`
- `deploy_cpu.sh`
- `deploy_gpu.sh`

### AC-09 ラベル情報自動反映

SVGから取得したラベル情報が、`function.yaml`および`model_handler.py`に反映されること。

### AC-10 モデル内部名自動反映

SVGから取得して正規化したモデル内部名が、出力フォルダ名、zipファイル名、Nuclio関数名、`function.yaml`内の関数識別名に反映されること。

### AC-11 複数人利用

複数ユーザーが同時に生成処理を行っても、それぞれ別々のjobとして処理され、ファイルが混ざらないこと。

### AC-12 進捗確認

ユーザーが処理中のジョブ状態を画面上で確認できること。

### AC-13 エラー処理

SVG解析、ONNX変換、ファイル生成、zip作成に失敗した場合、画面上にエラーメッセージが表示されること。

### AC-14 ローカルIPアクセス

同一LAN内の別PCから、サーバのIPアドレスを使ってWeb画面にアクセスできること。

### AC-15 Docker Compose起動

`docker compose up --build`で、web、worker、redisが起動し、Web画面にアクセスできること。

## 23. 実装時の注意

### 23.1 `.pt`の扱い

`.pt`ファイルはサーバ側で読み込むため、信頼できるローカルネットワーク内での利用を前提とする。

外部公開はしない。

### 23.2 SVGの扱い

SVGファイルは解析用の入力として扱い、出力zipには含めない。

SVG解析では、外部参照や危険なXML処理を避ける。

### 23.3 テンプレート差し替え

`function.yaml`、`main.py`、`model_handler.py`のどこを変更するかは、ユーザーが別途提示するCVAT exampleの変更仕様に従う。

この要件定義では、変更箇所の詳細までは固定しない。

### 23.4 `main.py`はできるだけ変更しない

`main.py`はCVAT/Nuclioとの入出力を担当するため、CVAT exampleからの変更を最小限にする。

主な変更は`function.yaml`と`model_handler.py`に寄せる。

### 23.5 出力ファイル名は固定

出力されるモデルファイル名は必ず以下とする。

```text
model.onnx
```

`main.py`や`model_handler.py`内でも、このファイル名を前提にする。

### 23.6 Webアプリ側で推論は行わない

本アプリケーションは、CVAT/Nuclioにデプロイするためのファイル一式を生成することを目的とする。

Webアプリケーション上で自動アノテーション推論を実行することは目的としない。

## 24. 最終ゴール

ユーザーがWeb画面から以下を入力する。

- 作成者名
- モデル表示名
- SVGファイル
- YOLO系骨格推定モデルの`.pt`ファイル

アプリケーションはSVGからモデル内部名とラベル情報を取得し、`.pt`を`model.onnx`へ変換する。

最終的に、ユーザーは以下の4ファイル入りフォルダをzip形式で取得できる。

```text
<model_internal_name>/
├── function.yaml
├── main.py
├── model.onnx
└── model_handler.py
```

このフォルダをCVAT/Nuclio環境に配置することで、自作YOLO系骨格推定モデルをCVATの自動アノテーション用モデルとして利用できる状態にする。
